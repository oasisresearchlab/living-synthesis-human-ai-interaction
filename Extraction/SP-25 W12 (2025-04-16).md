Claude:
> SP-25 Week 12 read [[@vaithilingamDynaVisDynamicallySynthesized2024]] (DynaVis), which blends a natural language interface with dynamically synthesized GUI widgets for editing visualizations. Discussion framed the problem (NLI gets you most of the way, but fine-grained tweaks are hard to discover and control), walked through the mechanism (LIDA data summary, Vega-Lite synthesis, static analysis, modular widgets), and read the study results (about 4x fewer prompts, higher self-rated ease, no significant workload or time differences). Contested points: whether constraining edits through a DSL narrows what users can do, whether the advantage would hold with newer models and better prompting, whether fluent programmers are better off editing code, and whether hiding the spec forgoes learning. Housekeeping opened with a steering-versus-prompting paper on cultural localization, and a tangent on how reliable LLM-generated code is led to inspecting HumanEval.

### Questions

- [[QUE - What would dynamically synthesized controls look like for post-editing machine translation?]]
- [[QUE - How might natural language interfaces help researchers invent visualizations for data that lack established visualization practices, such as discourse data?]]

### Claims
- [[CLM - natural language interfaces can get users most of the way to a visualization but make fine-grained iterative tweaks hard to discover and control]]
- [[CLM - synthesizing persistent GUI widgets from natural language edits removes the LLM round trip from later tweaks, which cuts the latency of iterative editing]]
- [[CLM - constraining LLM-generated edits to modular components through a domain-specific language prevents conflicting edits but narrows the space of possible modifications]]
- [[CLM - dynamic widgets add the most value for iterative fine-grained tweaking, while natural language suits known end states and larger exploratory changes]]
- [[CLM - for programmers fluent in the underlying specification language, editing code directly can be faster than LLM-mediated editing]]
- [[CLM - the reliability of LLM-generated code depends on how common and stable the target language or library is in web training data]]
- [[CLM - programmatic validation of LLM-generated code is more dependable than prompting the model to produce valid code]]
- [[CLM - interfaces that hide generated code behind widgets may deepen user dependence and forgo chances to learn the underlying representation]]
- [[CLM - explicit prompting cannot be assumed to steer LLMs faithfully toward culturally local or marginal perspectives]]
- [[CLM - summarizing datasets to fit LLM context windows puts visualization fidelity at risk because salient features may be omitted]]
- [[CLM - code generation benchmark scores may overstate LLM reliability for real programming tasks because benchmark problems are simple and may overlap with training data]]

### Evidence

- [[EVD - participants self-rated visualization editing tasks as easier to complete with DynaVis than with an NLI-only baseline - @vaithilingamDynaVisDynamicallySynthesized2024]]
- [[EVD - DynaVis and an NLI-only baseline showed no statistically significant differences in NASA TLX cognitive load or task completion time - @vaithilingamDynaVisDynamicallySynthesized2024]]
